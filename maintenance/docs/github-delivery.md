# GitHub交付能力核验与故障分类

## 先发现完整操作，再判断能力

维护使用已经连接的GitHub服务。先加载GitHub的完整操作清单（不带关键词过滤），再按需要查询create_branch、create_file/update_file、create_tree/create_commit/update_ref、create_pull_request和merge_pull_request的实际schema。某次筛选没有列出操作，不证明连接只读；历史成功也不保证未来会话一定提供相同操作。只调用本次真实发现的接口，不能虚构函数或用只读fetch进行写入。

写入已获维护者授权时，字段齐全后实际调用适合当前任务的写操作，而不是反复只做发现。优先创建或使用本批分支，绝不为了测试权限写main或其他仓库。分支已存在先读HEAD与diff；已有PR先核对它，不重复恢复旧包。正常的小批次写入就是能力验证，不另建空的测试PR。

## 分开报告四类状态

1. **可调用操作**：本次接口是否实际提供写入/合并。工具发现不完整时扩大清单或检查已安装连接，不能直接说仓库无写权限。
2. **远端授权与保护**：get_repo返回的push/maintain/admin是权限线索，不是所有端点必能调用的证明；以具体操作响应为准。Contents写入成功不证明Administration端点可用。遇401/403、必需审批或环境保护则报告准确阻塞，不绕过、不更换身份、不关闭保护。
3. **本地网络**：本地git的DNS、代理或连接错误只说明该网络路径失败，不代表GitHub连接器也失败。已经存在可用的正常连接器写入路径时使用它，不要求重新授权或让维护者手工代做。
4. **交付阶段**：本地提交、远端分支、PR、精确head CI、正常合并、main验证、Pages部署分别核验。只有对应合并提交的Pages deploy成功才称上线；工具发现或准备artifact成功不算发布。

## 正常交付与恢复

每次先读最新main和未合并PR。记录精确BASE_SHA；准备变更只写本批分支，生成数据必须运行build_catalog.py。常规写入可用Contents API，也可用Git objects构建树和提交后以force=false快进本批ref。远端拒绝或HEAD并发变化时重新协调，不能强制覆盖。

保留的恢复包只作为候选：先比对远端实际进展、完整树和源记录，不重跑旧迁移器覆盖后续论文。能够使用现成远端分支时，不再上传旧包。准备工作流只能在获授权本批分支执行可审阅、哈希核验的代码并正常提交；不得通过工作流取得更高权限、修改保护或用失败检查换取发布。

创建PR后审查真实diff与一手来源，检查精确head所有必需CI（包括全部HTTP浏览器回归）。留下诚实的助手自检说明，不伪造第二个审批身份；正常merge使用expected_head_sha。合并前重新读main/PR HEAD。合并后同一 main SHA 只需核实 generated-files check、Pages deploy 与 production smoke；不要等待一套重复的 Firefox/WebKit 全量回归。安全分支清理由每周 schedule 或手动 workflow 独立执行，不再作为每次发布的尾部步骤。

周更与人工触发批次均按本规则执行。持续出现的工具发现缺失应描述为当前操作可用性问题；不要笼统声称仓库权限丢失，也不承诺工具可用性永远不会变化。
